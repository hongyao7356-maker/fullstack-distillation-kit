# P0｜需求定义与验收边界

目标：建立范围与成功定义，而不是开始编码。

输入：用户场景、当前源码、历史约束、相关人员。盘点现有功能、环境依赖、运营流程与未知点。

步骤：
1. 画出角色/业务事件/边界；区分事实、推断、决策。
2. 将业务诉求拆成用户故事与可测 Given-When-Then 验收条件，标 P0 必须和以后可选。
3. 梳理非功能需求：响应时间、可用性目标、隐私、合规、运维成本，不得凭空设定 SLA。
4. 对关键需求做风险及反例（数据不一致、系统掉线、误授权、误操作）。
5. 写未决问题清单；未决定的事项不会自动变成开发任务。

交付：`.fullstack/docs/00_requirements.md` 和 `.fullstack/docs/00_acceptance.md`。

关键反例：如果用户仅说“第一时间回复客户”，不得擅自推断渠道合法性、答复权限或具体秒数。

验收：每个 P0 必须需求都有可测条件、数据来源与责任边界。
