# 知识蒸馏操作手册（可重复）

## 核心产物不是摘要，而是“可执行原则卡”

每条规则必须有四个链路：`具体事实 → 工程决策 → 适用前提 → 复验动作`。缺任意一个，先当候选资料，不得作为必须遵守的硬规范。

### 采样步骤

1. 围绕当前问题开研究题，例如“多租户客服系统怎样避免客户越权查价”。不要一口气读取全部仓库。
2. 从 source_registry 查两个来源，获取 README/文档、实际测试与 CI 路径、Issue/PR 讨论。代码行为、测试及实际历史比宣传文字更可靠。
3. 固定证据：存储链接、所在目录/文件、版本 SHA 或访问日期（如确实获得），只摘极短片段；最好写概括。
4. 归类：主张是作者明确说的、代码实际表现的，还是我们的工程推断？分别标注。
5. 反证：不同技术栈、不具备条件时为什么可能失效；有哪些备选方案。
6. 提炼规则 `IF 条件 THEN 行动 BECAUSE 机制 VERIFY 检查`。
7. 用 validator 检查卡片完整性，再在一个实际项目中验证。实践后的成功/失败、成本和改进另存复验记录。

### 四位专家的角色（不代替来源证据）

- Kent C. Dodds / Epic Stack：全栈项目工程基线、测试及生产发布准备。
- Antonio Erdeljac / Code With Antonio：从零构建完整功能的教程顺序；教程实录须用户依法取得，不能因为链接存在便假设已研读。
- Steven Tey / Dub：活跃商业开源产品的组织方式和迭代痕迹，不能从仓库结构反推出个人决策。
- Theo / T3 Stack：约束技术选择、端到端类型安全与模块化。

### 判定可信度

- A：固定 commit 的代码 + 相应自动测试/PR 讨论，直接支持具体主张。
- B：官方当前 README/文档，支持原则性主张，但可能随时间变化。
- C：演讲/博客/教程内容，需区分个人偏好与普适事实。
- D：二手摘要/未复核视频观点，只能列为候选。

### 重要限制

不经复核不得宣称“该开发者通常一定这样做”。不要把仓库的 CI 检查误认成项目所有质量保证。不允许从单一 successful tutorial 推导生产 SLA。未获授权不得下载会员视频、转存整篇文章、拷贝完整课程代码。
